# 奇偶校验文件卷（Parity File Volume）

用 Python + FastAPI + SQLite 实现的三盘条带化文件卷：每个文件按固定条带
（默认 512 KiB）切成 **两份数据块 + 一份 XOR 异或校验块**，分散存放在三个
相互独立的持久目录中。任一单盘故障，已确认上传的文件仍可下载；换上空盘后
后台自动重建冗余，重建期间允许继续上传。已入卷文件还支持**补丁式覆盖写**：
值班员拿到校准数据后，按字节偏移回填预留字节，只重写补丁涉及的条带。

## 目录布局

```
parity-volume/
├── app/
│   ├── coding.py        # XOR 编码 / 任意两块重建第三块
│   ├── storage.py       # 块文件原子写、换盘归档
│   ├── db.py            # SQLite 元数据（WAL，文件/条带/块/磁盘/重建任务）
│   ├── volume.py        # 上传、下载恢复、下线、换盘、重建、崩溃恢复
│   ├── main.py          # FastAPI 路由与异常映射
│   └── web/index.html   # 单文件操作网页（无构建步骤）
├── tests/selftest.py    # 端到端自测（真实 uvicorn + HTTP）
├── Dockerfile
├── docker-compose.yml
└── requirements.txt
```

三个“盘”是三个持久目录（生产环境应分别挂载到不同物理盘/独立卷），
SQLite 元数据放在第四个独立目录 `data/meta/`，单盘故障不影响元数据。

## 快速启动

```bash
docker compose up --build
# 打开 http://localhost:8000
```

无 Docker 时本地运行：

```bash
pip install -r requirements.txt
PV_DATA_DIR=./data PV_DB_PATH=./data/meta/volume.db \
  uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 网页操作

* **上传**：点击或拖拽文件。只有三块块全部落盘并提交元数据后，文件才会
  出现在“已确认文件”列表中。
* **补丁覆盖**：在“补丁覆盖”面板选择已入卷文件、填写从 0 起算的字节偏移、
  选择补丁文件后提交。只重写补丁涉及的条带（每个条带仅 `d0` 与 `p` 两个块，
  全零的 `d1` 不变），文件编号与长度保持不变，提交时同步重算 SHA-256 摘要
  并把版本号加一。
* **下线**：把某盘标记为故障（模拟拔盘）。
* **换空盘并重建**：旧盘目录归档为 `diskN.failed-<时间戳>-…`，原位建立空
  目录，后台线程按条带用其余两块盘重建；页面每 2 秒刷新进度。
* **下载/删除**：对已确认文件操作；下载时若有盘下线，自动用剩余两块在线
  重建数据。

## 补丁覆盖的正确性设计

| 需求 | 实现方式 |
| --- | --- |
| 三盘在线才可覆盖 | 覆盖前逐盘核对状态（含目录存在性对账），任一盘 `offline`/`rebuilding` 直接 503 拒绝，不写任何块 |
| 补丁越界拒绝 | 校验 `offset >= 0`、补丁非空、`offset + 补丁长度 <= 文件长度`，越界返回 400 `patch_out_of_bounds`，文件与版本不变 |
| 只重写涉及条带 | 按覆盖区间算出受影响条带，逐带把补丁合并进旧 `d0` 后原子重写（tmp+fsync+rename）`d0` 与 `p`；未涉及条带的三个块字节不变，自测用全盘块快照核对 |
| 保留文件编号与长度 | 不新增/删除条带，`files` 行原地更新；仅 `sha256`、`version`、`status` 变化，`id`/`size`/`stripe_count` 保持 |
| 提交时更新摘要 | 全部条带重写完成后，流式重算整文件 SHA-256，与状态恢复 `confirmed`、版本加一放在同一个 SQLite 事务提交 |
| 下载只能得到完整旧版或完整新版 | 每文件一把锁，覆盖与下载互斥；下载在锁内把完整内容读到临时文件后才返回，不会读到半新半旧的条带 |
| 写盘失败整体不生效 | 覆盖前把涉及条带的三个旧块备份到 meta 目录的 `overwrite-rollback/`（`preparing→prepared` 阶段门）；中途任一写失败，用备份逐块原子恢复，文件恢复 `confirmed`，任务记 `failed`，备份目录清理 |
| 服务重启后未提交覆盖不生效 | 覆盖期间文件置 `overwriting`（下载不可见），任务状态持久化在 `overwrite_jobs`；启动恢复发现未完成任务一律按备份回滚并清掉备份，已提交（`done`）的覆盖不受影响 |
| 覆盖成功后单盘离线可下载新版 | 覆盖写入的仍是标准三块条带（`d0 XOR d1 XOR p = 0`），任两块即可重建；自测逐盘下线核对新版内容 |

## 关键正确性设计

| 需求 | 实现方式 |
| --- | --- |
| 单盘故障可读 | 每条带 3 块等长、`d0 XOR d1 XOR p = 0`，任两块可重建第三块；下载逐带恢复并按记录长度裁掉零填充 |
| 重建期间可上传 | 新条带直接三盘写入（含重建中的新盘）；重建收尾再全盘扫描，确认新条带在新盘上不缺失才置 `online` |
| 残缺条带不会标健康 | 条带先以 `healthy=0` 入库，三个块原子写（tmp+fsync+rename）完成后才置 `healthy=1`；重建只扫描健康条带 |
| 上传中断/重启 | 未确认文件（`status='uploading'`）启动时连同块文件一并清除，永不可见；已确认文件不受影响 |
| 重建中断/重启 | 重建任务持久化在 `rebuild_jobs`，重启后自动续跑；块写入幂等，重复重建同一条带结果一致 |
| 超一盘失效 | 可读块不足两块时返回 HTTP 503 `{"error":"unrecoverable"}`，明确报不可恢复 |
| 降级拒绝残缺写入 | 任一盘 `offline` 时上传直接 503 拒绝，不会写出只有两块的新条带 |
| 物理丢盘识别 | 运行时对账：在线盘目录消失自动转 `offline`；已有部署启动时先检测后建目录，不会掩盖真实丢盘 |

## HTTP API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/status` | 磁盘状态、重建进度 |
| GET | `/api/files` | 已确认文件列表（含版本号与 SHA-256） |
| POST | `/api/files` | multipart 上传 |
| POST | `/api/files/{id}/patch` | 补丁覆盖：表单字段 `offset`（从 0 起算字节偏移）+ `patch`（补丁文件）；越界 400、盘不齐 503、失败自动回滚 |
| GET | `/api/files/{id}` | 下载（必要时自动重建） |
| DELETE | `/api/files/{id}` | 删除文件及其全部块 |
| POST | `/api/disks/{0..2}/offline` | 磁盘下线 |
| POST | `/api/disks/{0..2}/replace` | 换空盘并启动重建 |

## 已知边界

* 条带布局为固定的“2 数据块 + 1 校验块”，只容忍单盘故障（题目要求范围）。
* 块级静默腐化（bit rot）仅在三盘齐全时靠下载时的奇偶校验发现，没有后台
  定期巡检任务。
* 上传为单请求流式处理，未实现断点续传；大文件占用条带数 × 512 KiB 的
  三盘空间（含零填充的末条带）。
* 补丁覆盖是**原地等长回填**：只支持落在文件现有长度内的偏移与长度，
  不能借补丁扩展或截断文件；覆盖前要备份涉及条带的三个旧块，备份量与
  补丁涉及的条带数成正比（存放在 meta 目录，提交或回滚后立即清理）。
* 覆盖与同文件的下载/删除互斥执行；不同文件之间互不阻塞。
